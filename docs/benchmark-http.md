# Fixture HTTP trace overhead benchmark

Run this only when you explicitly want the local fixture benchmark:

```powershell
node scripts/run-tests.mjs scripts/benchmark-http-trace.mjs
```

The script is outside the default `test/` discovery tree, so `node scripts/run-tests.mjs` does not run it. The explicit run executes three paired rounds in alternating baseline/traced order. Each condition starts a fresh temporary FlowAtlas workspace and the same deterministic native HTTP ESM app. It sends 50 warm-up requests followed by 1,000 measured requests at concurrency 8, checks every status and response body, and records the request-ID and workload digests to demonstrate equal inputs. Each request has an absolute 10 second deadline and each condition has a 30 second readiness/workload deadline; there are no business retries. One additional unmeasured local metrics request reads fixed request-count, CPU-time, and RSS fields from the fixture after the measured workload. It is sent in both conditions but excluded from the workload latency samples.

Each traced app must produce exactly 1,051 HTTP spans: one SERVER span per warm-up/measured request plus the extra metrics request. The benchmark records the exporter summary fields `httpSpans`, `invalidSpans`, `delivered`, `dropped`, `queued`, and `inFlight`; it checks delivered plus dropped reconciles to total spans and records capture acceptance only with zero drops, invalid spans, or pending spans. `delivered` means the collector returned a successful response; a dropped/unacknowledged batch may have reached storage before its response was lost, so a nonzero drop count does not prove every such span is absent. Traced shutdown asks the inspector to flush over IPC and waits for the inspector process `close` event before reading its final output. Baseline has no SDK spans. The action history keeps at most 100 graphs, so its row count is not the total request or capture count.

The JSON artifact is written to `reports/benchmarks/` on success or failure. It contains raw per-request latency samples for the measured requests, per-condition p50/p95/p99, throughput, paired p95 delta in milliseconds and relative percent, fixture process CPU/RSS, counts, runtime/OS, source commit/digest, and validation flags. It does not include app source, URLs, bodies, request headers, or the session token. If baseline p95 is below 1 ms, the performance acceptance check uses an absolute 5 ms p95 overhead budget; otherwise it uses a 10% relative p95 increase target. The selected per-round and aggregate criterion is recorded. Performance target misses are reported but do not fail the measurement run by themselves.

Each run uses an isolated random directory under `reports/storage/benchmark-http-*`. The script stops the inspector through its stdin control, waits up to 12 seconds for its normal stop path and then uses a bounded final watchdog, checks that the writer lock is gone, then deletes only the validated generated workspace. If process shutdown, exporter drain, or lock checks fail, it does not claim process cleanup, keeps the fixture directory, and records its relative path in the report for diagnosis. Review retained directories manually before removing them.

This is a local fixture measurement of the full inspector, collector, exporter, and JSON storage path. It is not a real-app pilot, a production-load result, or a compatibility claim for other Node/OS combinations. Results can vary with filesystem, host load, and runtime. The benchmark does not decide the JSON storage backend on its own; collect repeatable evidence before changing that design.

## Complete paired evidence requirement

Performance acceptance now includes assessable, completedPairs/expectedPairs and a fixed reason. Only all three matching baseline/traced pairs with valid1000-request measurements and correctresponses may produce a verdict. Missing, short, invalid or mismatched conditions yield assessable=false/met=null, reason=incomplete_or_invalid_pairs, and null aggregate values. Diagnostic profiled runs likewise yield reason=profiled_run; their raw per-condition timings remain available for diagnosis. Existing thresholds remain10% relative or5ms for baseline<1ms. Capture/workload failures still fail the benchmark, and a performance target miss alone still does not fail measurement.
